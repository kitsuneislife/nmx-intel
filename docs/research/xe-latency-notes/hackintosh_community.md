# Hackintosh community reports: lag / slow GPU submission on Xe-LP iGPUs (Apple TGL/ICL drivers via kexts)

Scope note: research done 2026-11-13/14. The WhateverXe issue tracker (b00t0x/WhateverXe) was dumped in full through the
GitHub API (124 issues/PRs, all opened 2026-11-02 .. 2026-11-13) and grepped locally for lag/latency/frequency/RPS/GuC
terms; WhateverXe and WhateverGreen sources were read directly. Forum coverage (InsanelyMac, tonymacx86, Reddit,
OSXLatitude, Chinese forums) was thin: searches returned no thread matching the symptom, and OSXLatitude returned HTTP 522.

## Q1. GitHub repos (WhateverXe and forks, WhateverGreen, NootedBlue, etc.): issues/PRs/commits about lag, frequency, GuC, RPS, scheduling

### Takeaway
No WhateverXe issue describes our exact symptom: Metal jobs that wait 10-20 ms before they start while an Electron app is visible, on an otherwise accelerated desktop. Every "laggy UI" report in the tracker comes from machines where acceleration failed (software rendering). The relevant findings are code and adjacent bugs. (1) WhateverXe 0.8.x installs a "host RPS" hook only when `-disablegfxfirmware` is set; `-wex-no-host-rps` turns it off. (2) WhateverGreen's older `rps-control` takes a different approach: it forces max frequency (RP0) on every execlist submission. (3) Apple's host scheduler (`IGScheduler5`) shows stall/timeout bugs under load on Xe. (4) The Metal driver has Chromium/Electron-specific defects: a per-command-buffer leak and a 2D/3D blit race.

### Cited Findings

**WhateverXe host RPS (GPU frequency control when GuC is off)** [measured: read in source]
- WhateverXe hooks `AppleIntelFramebufferController::pmNotify(unsigned,unsigned,unsigned long long*,unsigned*)`. The code comment says: "the exact donor pmNotify is an Unsupported stub. Fulfill only the non-GuC frequency query, preserving the native writer/timer/idle transitions." The hook answers event 1 with `max(requested, boost)` from controller fields `+0xec8`/`+0xecc`, clamped to the RP caps read at MMIO `0x145998`: lo = bits 23:16, hi = bits 7:0, and it bails out if hi > 85. It encodes the result as `(f*3)<<23` ("50 MHz policy units -> 16.67 MHz hardware units"). When a check fails, it falls back to Apple's stub. — [kern_xe.cpp (b00t0x/WhateverXe main)](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)
- The hook is installed only if `-disablegfxfirmware` is present and `-wex-no-host-rps` is absent, on two paths. The ADL/RPL path (`adlnNativeRequested`) publishes `N97HostRPSRequested` / `N97HostRPSReady` in the IORegistry root. The TGL path publishes `TGLHostRPSReady`. Its comment reads: "Diagnostic A/B: omit only r285's host frequency callback ... Remove the argument to restore frequency control." `-tglnohostrps` also appears in the boot-arg fixture list. — [kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp); [tests/fixtures/boot_argument_names.json](https://github.com/b00t0x/WhateverXe/blob/main/tests/fixtures/boot_argument_names.json)
- Installation needs an exact match: symbol `__ZN31AppleIntelFramebufferController8pmNotifyEjjPyPj` at image offset `0x12BB4`, plus an 18-byte stub compare. If Apple's binary differs, `...HostRPSReady` = false and the GPU gets no host frequency requests. — [kern_xe.cpp `XE::xelpInstallHostRPS`](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)
- A built-in observation property, `TGLPowerSample` (OSSerializer on the framebuffer controller, schema 285, capped at 512 reads per boot), samples `0x1381b4`, `0x138108`, `0x145960` and `0x145948`. The comment reads: "Linux v6.12: GEN12_RPSTAT1[19:11] * 50/3 MHz; RC6 ticks are 1280 ns". The property also carries the requested/boost values, GuC/residency flags, host-RPS calls/answers, the last encoded request and the RP caps. This allows a direct check of GT frequency/RC6 during the lag. — [kern_xe.cpp `tglPowerSerialize`](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)

### Inferences
- [inferred] Two different host-side frequency policies exist. WhateverGreen's `rps-control` always requests RP0 on submit (Q3). WhateverXe's host RPS passes through Apple's requested/boost value. If Apple's requested value stays low while Electron keeps the GPU lightly but constantly busy, queued work would run slowly at low GT clock, and small jobs would wait behind it. This is testable: read `TGLPowerSample` (RPSTAT1 frequency) during the lag, and A/B `-wex-no-host-rps`.
- [inferred] #57 shows PCODE pinning the GT at 100 MHz under CPU load (PL1). Our symptom is reported as "not CPU bound", but package PL1 still deserves a check during the Electron case.
- [inferred] The `IGScheduler5::checkForProgress` stalls (#40, #44) show that Apple's host scheduler on Xe (execlists, no GuC) misbehaves under load. Its preemption/timeslicing between contexts may be the real cause of the queueing: small WindowServer jobs waiting behind Chromium's command buffers. No report confirms this.

### Gaps
- No WhateverXe issue or commit measures submit latency or frequency under multi-app load. I found no direct report of "typing lag with Electron visible".

- NootedBlue/NootedGreen sources (the `libxedrv` notes cited in #72) were not reachable.

## Q3. Ice Lake / Tiger Lake: WhateverGreen `igfxfw` (GuC) vs `-disablegfxfirmware` (host scheduling): known performance differences

### Takeaway
WhateverGreen has three firmware modes: host scheduler without GuC, reference scheduler with GuC, and Apple GuC scheduler (`igfxfw=2`). Its RPS-control patch, which requests max frequency at every execlist submission, exists only for SKL/KBL/CFL/CML, not Ice Lake. Community guidance says Apple GuC is buggy. I found no benchmark comparing GuC with host scheduling on Ice Lake, or on Tiger Lake under Apple's drivers.

### Cited Findings
- WhateverGreen enum `FirmwareLoad`: `FW_DISABLE = 0 /* Use host scheduler without GuC */`, `FW_GENERIC = 1 /* Use reference scheduler with GuC */`, `FW_APPLE = 2 /* Use Apple GuC scheduler */`. — [kern_igfx.hpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.hpp)
- README: `igfxfw=2` / `igfxfw` property = "Force loading of Apple GuC firmware"; `igfxrpsc=1` / `rps-control` = "Enable RPS control patch (improves IGPU performance)". — [WhateverGreen README](https://github.com/acidanthera/WhateverGreen)
- How RPS control works: it routes `pmNotifyWrapper` and always returns `GEN9_FREQ_SCALER << 23 * RP0` (RP0 read from `GEN6_RP_STATE_CAP & 0xFF`), with the comment "Request the maximum RPS at exec list submission ... we are still getting proper power management due to force wake clears". It also NOPs a `jnz` in `IGHardwareCommandStreamer5::submitExecList`, because "`submitExecList()` only controls RPS for RCS type streamers. Patch it to enable control for any kind of streamer". — [kern_igfx_pm.cpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx_pm.cpp)
- On Ice Lake, WhateverGreen sets `supportsGuCFirmware = true` but does not set `modRPSControlPatch.available`. RPS control is available only for SKL/KBL/CFL/CML, so `rps-control` is a no-op on ICL. — [kern_igfx.cpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.cpp)
- Changelog history: "Recovered GuC loading for internal usage (do NOT use, causes freezes and crashes)"; "Added `igfxfw=2` boot argument and `igfxfw` IGPU property to load Apple GuC firmware"; "Added the use of RPS control for all the command streamers"; "Disabled RPS control patch by default due to a bug in 10.15.6 IGPU drivers"; "Allowed enabling `igfxrpsc` on Comet Lake". — [WhateverGreen Changelog](https://github.com/acidanthera/WhateverGreen/blob/master/Changelog.md)
- Community guidance (Coffee Lake focus; credited to 5T33Z0): Apple GuC "improves Intel Quick Sync Video and iGPU performance ... It's buggy and not advisable to use". RPS control "Improves iGPU performance". "There are comments of OC developers saying that `rps-control` is better than `igfxfw` (Big Sur and newer) because of the bug that seems to be in Apple GUC." Symptoms that call for these knobs are listed as "low max frequency, fixed frequency that does not vary, screen glitches". — [perez987/Intel-UHD-630-on-macOS](https://github.com/perez987/Intel-UHD-630-on-macOS)
- Ice Lake: `igfxfw=2` is the listed fix for the "EL[0] was invalidated!!" error ([acidanthera/bugtracker#1343](https://github.com/acidanthera/bugtracker/issues/1343)). This is a correctness issue with host execlists on ICL, not a performance issue. — [m0d16l14n1/icelake-hackintosh](https://github.com/m0d16l14n1/icelake-hackintosh)
- The WhateverGreen setup guide tells users to delete `-disablegfxfirmware` (WhateverGreen handles firmware itself). — [FAQ.IntelHD.en.md](https://github.com/acidanthera/WhateverGreen/blob/master/Manual/FAQ.IntelHD.en.md)
- Tiger Lake with WhateverXe: loading GuC fails ("GuC load STATUS 0x830000EC"), so host scheduling is the only mode that works today. — [WhateverXe #48](https://github.com/b00t0x/WhateverXe/issues/48)

### Inferences
- [inferred] On Apple's driver, host scheduling relies on the `pmNotify` path for frequency requests. On SKL-CML, the community fix for low or stuck frequency was to force RP0 per submission (`rps-control`). WhateverXe's host RPS is the Xe equivalent, but a gentler one (requested/boost, not RP0). A "force RP0" variant is the closest proven precedent to try as a single-variable test.
- [inferred] The RCS-only RPS check that WhateverGreen removes probably also exists in the TGL `IGHardwareCommandStreamer5::submitExecList`. In that case, blit (BCS) submissions would never request frequency under WhateverXe. This was not verified in the TGL binary.

### Gaps
- I found no measured comparison (latency or FPS) of GuC vs host scheduling on Ice Lake or Tiger Lake under macOS.
- It is unknown whether Apple's TGL `submitExecList` has the RCS-only RPS gate. Checking needs a disassembly of AppleIntelTGLGraphics.
