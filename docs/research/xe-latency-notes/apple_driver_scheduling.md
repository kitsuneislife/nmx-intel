# Apple Intel GPU driver scheduling (ICL/TGL): GuC vs host scheduler, preemption, priorities

Evidence legend: **[measured]** = read directly on this machine (Raptor Lake-P, Sequoia 15.8.1, WhateverXe + Apple TGL donor kext, 2026-11-13); **[documented]** = stated in source code or docs of a third party; **[inferred]** = my reasoning; **[unverified]** = not confirmed.

Local evidence files (cited as `file://` below):
- Apple TGL accelerator binary: `/Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics` (SHA-256 prefix `6c8ab6cc`), its `Info.plist`, live `ioreg -c IntelAccelerator`, live `sysctl debug.intel`.
- WhateverGreen source (`kern_igfx.cpp/.hpp`, master) and WhateverXe source (`b00t0x/WhateverXe`, commit `2bad717`, 2026-11-13).

## Q1. What do WhateverGreen / WhateverXe sources and Apple symbol names say about GuC vs host scheduler paths, timeslicing and preemption?

### Takeaway
Apple's Intel driver has a selectable scheduler (`GraphicsSchedulerSelect` in the `Development` dict of the `IntelAccelerator` personality). On this machine it is 5 = **"Host Preemptive"**: the host (execlist) scheduler is preemptive by design, with preemption enabled, a 160 µs preemption delay and a 2000 µs preemption timer. The host scheduler does have preemption. WhateverXe does, however, disable 3D *object-level* (mid-draw) preemption on TGL as a hardware workaround, so a single long draw can't be preempted.

### Cited Findings
- WhateverGreen documents the scheduler selector values used by Apple's driver: "1 - Automatic scheduler (Apple -> fallback to disabled)", "2 - Force disable via plist (removed as of 10.15)", "3 - Apple Scheduler", "4 - Reference Scheduler", "5 - Host Preemptive (as of 10.15)". WEG writes `GraphicsSchedulerSelect` into the accelerator's `Development` dictionary (value 5 on Catalina+ when GuC is disabled) — [WhateverGreen kern_igfx.cpp, applyDevelopmentPatches](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.cpp)
- WEG's firmware modes: `FW_DISABLE = 0 /* Use host scheduler without GuC */`, `FW_GENERIC = 1 /* Use reference scheduler with GuC */`, `FW_APPLE = 2 /* Use Apple GuC scheduler */`; default on non-Apple firmware is FW_DISABLE. `igfxfw=2` = "Force loading of Apple GuC firmware". WEG hooks `IGHardwareGuC::loadGuCBinary`, `IGScheduler4::loadFirmware`, `IGHardwareGuC::initSchedControl` — [WhateverGreen kern_igfx.hpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.hpp); [WhateverGreen README](https://github.com/acidanthera/WhateverGreen/blob/master/README.md)
- WEG's GuC handling (`supportsGuCFirmware`) covers SKL..ICL/CML only; the Rocket Lake / Alder Lake cases do not enable it (WEG does not drive TGL/Xe) — [WhateverGreen kern_igfx.cpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.cpp)
- The Apple driver logs from a real machine (bugtracker #748, CFL) include "Selected Apple Firmware Scheduler", "Forced to use Host Preemptive Scheduler", "Graphics Scheduler Preemption Enabled!", and preemption delay 400 µs / timer 2000 µs — [acidanthera/bugtracker#748](https://github.com/acidanthera/bugtracker/issues/748)
- **[measured]** The Apple TGL binary contains the strings `Host Preemptive`, `IGScheduler`, `IGScheduler4`, `IGScheduler5`, `"Unsupported GraphicsSchedulerSelect=%u\n"@tgl/IntelAccelerator.cpp:2184`, `"Unexpected scheduler type!"@tgl/sched/IGScheduler.cpp:35`, `[IGPU] Selected %s Scheduler`, `[IGPU] Forced to use %s Scheduler`, `[IGPU] Failed to initialize graphics firmware. GuC code paths are `tgl/sched3/IGGuC.cpp` and `tgl/sched4/IGHardwareGuC.cpp` / `IGHardwareGuCWorkQueue.cpp` — [local binary](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics)
- **[measured]** The live `IntelAccelerator` `Development` dict on this machine contains `GraphicsSchedulerSelect=5`, `EnablePreemption=1`, `PreemptionDelayIntervalUS=160`, `PreemptionTimerIntervalUS=2000`, `SchedThrottleCapMS=100`, `SchedPmNotifyEnable=1`, `SchedulerFallbackOnFirmwareFail=1`, `EnableMultiContext=1`, `MetalCoalesce=1`, `SemaphoreWaitPoll=1`, `CsbProcModeSelect=0`, `SingleChannelIndex=0`, `WaitForComplete=0`, `RingSizeKB=32`, `EUThrottle=0`, `PixelBackendThrottle=0`, `SamplerPipeThrottle=0`, `SamplerDataFetchThrottle=0`. Other keys in the binary: `DisableTailCoalescing` — [local Info.plist](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/Info.plist)
- WhateverXe forces the same values itself: `const char *keys[] {"MultiForceWakeSelect","GraphicsSchedulerSelect"}; const unsigned values[] {1,5};` with the comment "Select real MMIO / refcounts, the existing host scheduler, and no GuC before parent start" (in the standalone-start path) — [WhateverXe kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)
- WhateverXe requires `-allow3d -disablegfxfirmware` for every configuration — [WhateverXe README](https://github.com/b00t0x/WhateverXe/blob/main/README.md)
- With `-disablegfxfirmware`, WhateverXe routes the Apple host-scheduler path. These symbols name the execlist submission and CSB handling: `IGHardwareCommandStreamer5::submitExecList(unsigned)`, `IGHardwareCommandStreamer5::processCSBDetail(SGfxContextStatusBufferEntry*, unsigned&)`, `IGHardwareCommandStreamer5::handleSoftwareContextSwitchInterrupt`, `IGHardwareRingBuffer::sleepForStamp(unsigned*, unsigned, unsigned)`, `ContextStatusBufferValidate(IGHwCsExecList5 const&, ...)`, `IGInterruptBridge::{enable,enableInterrupts,processInterrupts,serviceInterrupts}`. GuC symbols also present: `IGGuC::loadBinary(bool)`, `IGGuC::dmaHostToGuC(...)` — [WhateverXe kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)
- WhateverXe's host-scheduler wrappers are observation/diagnostic wrappers that call the original (`wrapTGLHostSubmit`, `wrapTGLHostWait`, IRQ wrappers). An opt-in rewrite of CSB intake (`-tglcsb12`, "Tiger Lake host-scheduler CSB intake") classifies the preemption CSB cases (PreemptToIdle, IdlePreempt, NewQueuePreempt, ActiveToIdlePreempt, LiteRestore). The source comments say some preempt-to-idle cases "need explicit unfinished-work/idle accounting" and are routed to `IncompleteToIdle` — [WhateverXe kern_tgl_csb.hpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_tgl_csb.hpp)
- **WhateverXe disables 3D object-level preemption on TGL**: "r135: TGL B0 object-preemption topology corruption (Vol14 UP3 p53)… clear only bit0" of the immediate written to CS_DEBUG_MODE1 (0x20EC) and CS_CHICKEN1 (0x2580) in `IntelAccelerator::startGraphicsEngine`. "r144: … Select the global 20EC bit0" by clearing bit 14 of 0x20E0 (FFSC per-context preempt control), so contexts cannot re-enable it. Registry flags `TGLObjectPreemptionDisabledReady` and `TGLObjectPreemptionGlobalReady` report this. A separate file disables "colored GSYNC for the B0 multicontext-preemption hang" — [WhateverXe kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp); [WhateverXe kern_tgl_gsync.hpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_tgl_gsync.hpp)
- In Linux i915 the timeslicing/preemption logic of the legacy execlists path is in the host driver. The GuC backend moves scheduling to firmware; the RFC notes timeslicing/preemption are hard to integrate with the DRM scheduler on execlists — [i915 GuC submission / DRM scheduler RFC](https://docs.kernel.org/5.19/gpu/rfc/i915_scheduler.html)

### Inferences
- [inferred] "Host scheduler = no preemption" is **not** right for Apple's driver. Mode 5 is explicitly "Host Preemptive", and preemption is enabled here (`EnablePreemption=1`). The preemption timer (2000 µs) and delay (160 µs) values suggest a pending higher-priority submission waits ~0.16 ms before a preempt request, with a 2 ms timer — well below the 10–20 ms stalls observed. So a missing preemption feature alone probably doesn't explain 10–20 ms waits.
- [inferred] What WhateverXe changed can widen the granularity: with 3D object-level preemption off, the RCS can only preempt at draw/command boundaries (not mid-primitive/object). A busy app issuing large draws (or long compute dispatches, if compute mid-thread preemption is also not in effect) can keep the engine for the full draw duration. That can produce multi-ms waits for a tiny job in another context.
- [inferred] Another plausible cause is that preemption is *requested* but completes as "preempt to idle"/lite-restore paths that the host scheduler handles slowly (via the software context-switch interrupt and CSB processing on a workloop). The 10–20 ms would then come from interrupt/workloop latency. `SchedThrottleCapMS=100` and the priority "credits" (Q4) may also hold low-priority clients.
- [inferred] `-disablegfxpreemption` (or `EnablePreemption=0`) gives an A/B knob to test whether preemption is active at all: if latency does not change, preemption isn't the active mechanism.

### Gaps
- I didn't read the disassembly of `IGScheduler5`/host scheduler to confirm the timeslice quantum and whether it preempts on priority only or also time-slices equal priorities. The string set has no "timeslice"/"quantum" key; no `SchedulerTimeslice` or `AppleIntelSchedulerSettings` string was found in the TGL binary.
- The boot log `[IGPU] Selected %s Scheduler` and `[IGPU] Graphics Scheduler Preemption ...` lines didn't show up in `log show --last boot` for sender AppleIntelTGLGraphics (they are probably IOLog/kprintf only). Confirming them needs `-v` / serial / `dmesg`.
- NootedBlue (ChefKissInc) source wasn't checked in this pass.

## Q2. Is GuC scheduling smoother than host scheduling? Is GuC feasible on Alder/Raptor Lake with Apple's TGL driver?

### Takeaway
I found no measured evidence that Apple GuC scheduling is smoother than host scheduling on any hackintosh. The only reports are about power management. GuC on ADL-P/RPL-P with Apple's TGL driver is very unlikely to work: Apple's driver loads an Apple-signed TGL GuC image and does an ME hash check, while Linux uses a different firmware family for ADL-P.

### Cited Findings
- On CFL laptops, `igfxfw=2` (Apple GuC) worked on few machines. One user reported "Idle pkg power went down from 2.8Watts to .9 Watts" (uncertain cause). Another stated "Apple GuC is required for proper power management, which does not work on non-Apple computers." vit9696: works on very few laptops, "Do not expect too much." GuC failures caused sleep issues and a GPU stuck at 350 MHz — [acidanthera/bugtracker#748](https://github.com/acidanthera/bugtracker/issues/748)
- WEG FAQ: "Apple GuC firmware doesn't work at old 22 nanometer chipsets - Z370 and older." — [WhateverGreen FAQ.IntelHD](https://github.com/acidanthera/WhateverGreen/blob/master/Manual/FAQ.IntelHD.en.md)
- **[measured]** The Apple TGL binary's GuC loader checks authentication through the ME: `"Graphics Firmware Load failed boot hash check!"@tgl/sched3/IGGuC.cpp:1466`, `[IGPU] Failed to get public key hash injected`, `[IGPU] Hash data from ME never returned, status = %x, failing load!`, `[IGPU] Failed to wake the ME.` — [local binary](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics)
- WhateverXe hooks `IGGuC::loadBinary` / `dmaHostToGuC` only for diagnostics ("TGLGuCDiagnosticRouted", GuC header panic capture) and still requires `-disablegfxfirmware`. Its ADL-N path asserts "No GuC uKernel and no render/copy interrupts owned by firmware" — [WhateverXe kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp); [WhateverXe kern_alderlake_n_gpu.hpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_alderlake_n_gpu.hpp)
- Linux i915: ADL-P left force-probe in 5.17, and its GuC firmware moved v62 → v69 → v70 (the "support v69 in parallel to v70" patch) — [intel-gfx, 2022-07](https://lists.freedesktop.org/archives/intel-gfx/2022-July/302105.html)
- Linux i915 default policy (`intel_uc.c`): TGL/RKL default to execlists (GuC submission off, HuC only); ADL-P and newer default to GuC submission. "Unblock GuC submission on Gen11+" made it possible on all Gen11+ given firmware — [intel_uc.c](https://codebrowser.dev/linux/linux/drivers/gpu/drm/i915/gt/uc/intel_uc.c.html); [PATCH 47/47 Unblock GuC submission on Gen11+](https://lists.freedesktop.org/archives/intel-gfx/2021-July/270955.html)

### Inferences
- [inferred] Linux uses separate `tgl_guc_*.bin` and `adlp_guc_*.bin` images, which suggests the GuC firmware is platform-specific. Apple's GuC is a different, Apple-built firmware with an Apple interface (`IGScheduler4`/sched3 `IGGuC`) that needs ME-based hash authentication. A TGL image for Apple's scheduler is unlikely to authenticate or run on ADL-P/RPL-P ME/GuC hardware. Treat "GuC on RPL-P with Apple's TGL driver" as **not feasible without major RE work**.
- [inferred] Even on genuine Apple GuC platforms, the gain reported is power, not latency. GuC isn't a promising lever for the 10–20 ms symptom.

### Gaps
- I didn't confirm the exact `adlp_guc_70.bin` / `tgl_guc_70.bin` contents or whether ADL-P GuC is binary-compatible with the TGL GuC ABI. I found no report of anyone trying `igfxfw=2`-style Apple GuC on TGL/ADL with WhateverXe.

## Q3. Known kext properties / boot args for Intel driver scheduling or power

### Takeaway
The real knobs are in the accelerator's `Development` dictionary (settable from a kext like WEG/WEX before start) and a handful of `debug.intel.*` sysctls, plus `-disablegfxfirmware` and `-disablegfxpreemption`. `IGAccelSchedulerMode`, `AppleIntelSchedulerSettings` and `SchedulerTimeslice` don't appear in the TGL binary.

### Cited Findings
- Scheduler/preemption keys (Development dict, live values above): `GraphicsSchedulerSelect`, `EnablePreemption`, `PreemptionDelayIntervalUS`, `PreemptionTimerIntervalUS`, `SchedThrottleCapMS`, `SchedPmNotifyEnable`, `SchedulerFallbackOnFirmwareFail`, `CsbProcModeSelect`, `SingleChannelIndex`, `WaitForComplete`, `SemaphoreWaitPoll`, `MetalCoalesce`, `DisableTailCoalescing`, `EnableMultiContext`, `MultiForceWakeSelect`, throttles `EUThrottle`/`PixelBackendThrottle`/`SamplerPipeThrottle`/`SamplerDataFetchThrottle` — **[measured]** [local Info.plist](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/Info.plist)
- Boot args present in the TGL binary: `-disablegfxfirmware`, `-disablegfxpreemption`; log string "Graphics preemption disabled via NVRAM" — **[measured]** [local binary](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics)
- WEG boot args/properties: `igfxfw=2` (Apple GuC), `igfxrpsc=1` / `rps-control` ("Enable RPS control patch (improves IGPU performance)"), `igfxagdc=0` / `disable-agdc`, `-igfxblr` / `enable-backlight-registers-fix`, `-igfxmlr` / `enable-dpcd-max-link-rate-fix` and `dpcd-max-link-rate`. `forceRenderStandby=0` disables RC6 — [WhateverGreen README](https://github.com/acidanthera/WhateverGreen/blob/master/README.md); [WhateverGreen FAQ.IntelHD](https://github.com/acidanthera/WhateverGreen/blob/master/Manual/FAQ.IntelHD.en.md)
- `MultiForceWakeSelect`: "0: Framebuffer's SafeForceWake; 1: IntelAccelerator::SafeForceWakeMultithreaded… Forcing 0 will result in hangs" — [WhateverGreen kern_igfx.cpp](https://github.com/acidanthera/WhateverGreen/blob/master/WhateverGreen/kern_igfx.cpp)
- WhateverXe-specific: `-allow3d`, `-disablegfxfirmware` (required), `-igfxdvmt`, `-tglcsb12` (opt-in CSB intake), `-wex-adln-qtrace` (ADL-N queue trace hooking `IGAccelCommandQueue::processCommandBuffer` and `IOAccelCommandQueue::getOwningTaskPid`) — [WhateverXe README](https://github.com/b00t0x/WhateverXe/blob/main/README.md); [WhateverXe kern_xe.cpp](https://github.com/b00t0x/WhateverXe/blob/main/WhateverXe/kern_xe.cpp)

### Inferences
- [inferred] Cheap A/B experiments on this machine: (a) `-disablegfxpreemption` to see if preemption currently helps or hurts; (b) inject `Development` overrides (`PreemptionTimerIntervalUS`, `PreemptionDelayIntervalUS`, `SchedThrottleCapMS`, `MetalCoalesce=0`, `DisableTailCoalescing`) from WEX/a small kext the same way WEG/WEX set `GraphicsSchedulerSelect`. The binary clamps the preemption intervals ("Constraining … in the range [%u,%u] us").
- [unverified] AGPM `IGPU` entries and `AGDCEnabled` are power/display-policy knobs. Nothing found ties them to submit latency.

### Gaps
- The clamp ranges for the preemption intervals and the semantics of `CsbProcModeSelect` values weren't extracted (needs disassembly).

## Q4. macOS Metal / IOAccelerator priority model: does WindowServer get a band that preempts app work on Intel?

### Takeaway
Apple's Intel scheduler has four software priority bands with per-band credits and priority-based preemption, plus a PID-elevation knob. Clients must be entitled to request priority changes, and WindowServer is identified explicitly. I found no public documentation; all of this is from strings and sysctls.

### Cited Findings
- **[measured]** Live sysctls: `debug.intel.schedPriCreditsHigh/NormalHigh/Normal/Low = -1` (default), `debug.intel.schedPriPreemption = 1`, `debug.intel.schedPriElevatePID = -1`, `debug.intel.schedEnableThrottleOverride = 0`, `debug.intel.schedThrottle{Low,Normal,NormalHigh,High}PriByVal = -1`. Log string `[IGPU] schedPriCredits%s %d -> %lld` — [local sysctl / binary](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics)
- **[measured]** Binary strings: `process_token_RequestPriorityLevel`, `[IGPU] [IGPU][GL] (pid=%u,name=%s,windowserver=%d) Priority change requested, but is not entitled!`, `WindowServer` — [local binary](file:///Library/Extensions/AppleIntelTGLGraphics.kext/Contents/MacOS/AppleIntelTGLGraphics)

### Inferences
- [inferred] Four bands (Low, Normal, NormalHigh, High) with credits look like a weighted/credit scheduler, where higher bands preempt lower ones (`schedPriPreemption=1`). WindowServer (compositor) probably sits in a higher band. A tiny job from a normal app at the *same* band as a busy visible app may wait for that app's credit/time window rather than preempt it. That fits "tiny jobs wait 10–20 ms whenever a busy app is visible".
- [inferred] `schedPriElevatePID` (a debug sysctl) may let one PID be elevated for a test, and `schedPriCredits*` may change band weights. Whether these are writable at runtime without `-v`/debug boot args is unverified. Writing them changes system state, so it needs Lukas's OK.
- [unverified] Public Metal has no per-`MTLCommandQueue` priority API on macOS; priority is set by the kernel driver from the task (entitlements / WindowServer).

### Gaps
- I found no Apple documentation of IOAcceleratorFamily2 / IOAccelEventMachine priority bands. On Sequoia `IOAcceleratorFamily2` lives in the kernel collection (no standalone binary at `/System/Library/Extensions/IOAcceleratorFamily2.kext/Contents/MacOS/`), so I didn't extract its strings.
- I didn't determine how Metal clients are mapped to bands (the default band of a normal app vs WindowServer) or the credit units.
