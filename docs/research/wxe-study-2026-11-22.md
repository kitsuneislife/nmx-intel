# How much of the i5-13420H the hackintosh uses, and is a WhateverXe fork worth it (2026-11-22)

> **Summary.** Measured and estimated how much of this laptop's hardware macOS uses today, compared with Windows
> and Linux on the same chip. Overall **~45-60 %** [inferred, wide range]. CPU clocks are the largest gap: single
> thread peaks at 3.55 GHz against a 4.6 GHz spec. Idle efficiency is the worst. Our AGPM profile carries the
> `RCxControl` block that kills GT RC6 (WhateverXe #87) [measured: present]. Most of the gain sits **outside**
> WhateverXe (CPU config, AGPM, power states), so the verdict is: no full fork, keep a thin patch series on upstream.

Related: [xe-latency.md](xe-latency.md), [radar-2026-11-22.md](radar-2026-11-22.md),
[xe-alternatives.md](xe-alternatives.md), [../knowledge/hybrid-route.md](../knowledge/hybrid-route.md),
`tools/cpu/clockprobe.c`, `tools/cpu/cpu-study.sh`.

## 1. The metric

**Extraction % = what macOS gets ÷ what the best of Windows or Linux gets on the same (or same-class) hardware**,
one number per area, then a weighted total. Windows is the 100 % reference because Acer tunes its firmware for it;
Linux is shown where it beats Windows.

## 2. Reference numbers (Windows / Linux)

- **CPU, Windows, this exact model (ANV15-51, i5-13420H):**
  - Cinebench R23: 13,731 MT / 1,860 ST (TechRadar).
  - Package power under load: ~104 W in the first seconds, ~79 W at 15-30 s, ~55 W sustained (LaptopMedia).
  - Geekbench 6 medians across sites: 2,186-2,320 ST and 8,444-9,760 MT (Notebookcheck, cpu-monkey, nanoreview).
- **CPU, Linux vs Windows:** Phoronix measured Linux ~14-15 % faster on CPU geomeans on Meteor Lake and Lunar Lake
  [measured by them, other chips; inferred to hold roughly here].
- **iGPU, Linux vs Windows:** the Intel iGPU is often a little slower on Linux than on Windows. Windows stays the
  iGPU reference.
- **Idle, Linux:** on an RPL-P XPS 13 Plus 9320 (same display IP as ours), Linux idles at **0.88 W package** with
  PC8 at 79 %. macOS with WhateverXe idles at 4.37 W and never goes below PC6 (jkbuha, WhateverXe #87).

## 3. Our machine today [measured 2026-11-22 19:20 unless noted]

- **Setup:** XE-15c (WhateverXe 0.8.3 + our patches), `-wex-objpreempt -wex-noccs -wex-hostrps-max`,
  `-disablegfxfirmware`, SMBIOS MacBookPro16,1, CPUID spoofed to Comet Lake.
- **Topology:** XNU sees 12 identical CPUs.
  - `hw.perflevel0.physicalcpu: 12`, no `perflevel1`.
  - `machdep.cpu.thermal.hardware_feedback: 0`, so no Thread Director/HFI.
  - CpuTopologyRebuild is in the EFI but disabled (`make_config.py` line 36). There is no CPUFriend.
- **CPU clock** (`clockprobe`: a dependent `add reg,reg` chain, one add per cycle, on AC, load average ~2.8):
  - Single thread: peaks at 3.55-3.56 GHz, then falls to 1.84-3.24 GHz. Windows boosts to 4.6.
  - 12 threads: 1.65-1.98 GHz per thread, 21.6 GHz-equivalent in total.
  - `pmset -g therm` shows `CPU_Speed_Limit 100` and no thermal warnings.
  - Caveat: the 2.8 load average from other apps lowers these numbers. `cpu-study.sh` repeats the run with power
    data.
- **iGPU:**
  - The GT is pinned at RP0 (1400 MHz requested, ~1.1 GHz granted). RC6 is never entered (XE-15).
  - FMA throughput is ~711 GFLOPS against a theoretical 1,075 (66 %).
  - GuC/HuC are off, so the CPU submits GPU work. The CCS ring is off (`-wex-noccs`).
- **AGPM:** `ioreg` has **one `RCxControl` entry**: `RC6_Wake_Limit=40, RC6_Threshold=520, RC_Eval_Interval=40000,
  RP_Idle_Hysteresis=25`. It sits next to a `CPGControl` entry.
  - These are the exact values rodgod-rr found killing GT RC6 50-80 s after boot on a MacBookPro16,1 RPL-HX (#87).
  - So our "RC6 never entered" is probably AGPM, not only `-wex-hostrps-max` [inferred, strong].
- **Bluetooth:** state Off (`BCM_4350C2`). The #87 PC2 blocker (Intel CNVi BT) probably does not apply as-is
  [unverified].

## 5. What is left, ranked by gain ÷ effort

1. **CPU clocks and power (config only, no kext code):**
   - First find why a single thread stops at 3.55 GHz. Suspects [unverified]:
     - the Acer EC performance mode carried over from Windows (Quiet/Balanced caps PL1/PL2);
     - EPP/HWP hints from the MacBookPro16,1 frequency vectors with no CPUFriend;
     - the iGPU pinned at RP0 with no RC6, using up the shared package budget;
     - E-core placement.
   - Then, one variable each: CPUFriend with a vector built for this chip, then CpuTopologyRebuild (#5 on the
     Dortania/b00t0x list; mixed anecdotes, one ~1535→1863 Geekbench ST report).
   - Gain: CPU rows from ~60 % toward ~90 %. Biggest single item.
2. **AGPM injector without `RCxControl`/`CPGControl` (codeless kext, ~30 lines of plist):**
   - rodgod-rr went from GT RC6 0 → 96 % and package PC2 0 → 89 % with it.
   - For us: lower idle power, cooler package, and more turbo budget left for the CPU (feeds item 1).
   - Test it alone, with `-wex-hostrps-max` unchanged.
3. **#130 fence timer (`IOAccelFenceMachine` quantum 100 ms):**
   - Not in 0.8.3 (no match in `src-083`).
   - gianguyen14 confirmed the binary site on **Sequoia 15.8.1**. With `-wexfencepoll` (2 ms quantum): 0 completions
     over 50 ms vs 90-150 ms stalls without it.
   - Small patch on our series; fits the lag work directly.
4. **Package C-states below PC6 at idle:**
   - Check `PKGC_BREAK_CAUSE_*` through IOReport `pmtelemetry_cpu` (no sudo needed).
   - Then look at PCH xHCI LTR and Bluetooth, as in #87.
5. **#176 governor:** already built (XE-15g). Only useful once RC6 works (item 2).
6. **Display DC states / PSR / DMC on display13:** large work. Upstream contributors with the same display IP are on
   it: jkbuha (RPL-P) on the ADL-P DMC loader, brandonedley on DC9 teardown for sleep (PC10 99 %). Follow, don't
   lead.
7. **GuC/HuC submission:** the root of CPU-dependent GPU latency and of missing HuC media/FairPlay (#48). The
   hardest item, and nobody has a working path. Not a goal.

## 6. Fork verdict

**No separate WhateverXe project.** Keep what we have: a short patch series (`0001..0004`) rebased on each upstream
release, plus one small kext or config change per item above.

- Items 1, 2 and 4 are not WhateverXe code. A fork would not get them faster.
- Upstream moves weekly (0.8.0 → 0.8.3 in two weeks). It has active contributors on our exact display IP and
  SMBIOS: jkbuha (RPL-P display13), rodgod-rr (RPL-HX, MacBookPro16,1).
- A hard fork would pay the rebase cost alone and lose their fixes.
- Where a patch is ours (objpreempt, noccs, fence poll), post it upstream as a PR or an issue comment with numbers.
- Revisit if upstream stalls for a month or rejects a change we depend on.

## 10. The board-id frequency vector, decoded (2026-11-22) [measured]

`X86PlatformPlugin.kext/Contents/Resources/Mac-E1008331FDC96864.plist` holds three 7,668-byte `FrequencyVectors`;
vectors 0 and 1 are identical and 2 differs only in four ratio thresholds. `machdep.xcpm.vectors_loaded_count 1`,
X86PlatformPlugin and X86PlatformShim are active, `plugin-type 1`. The tunables block at the end of each vector is a
list of 36-byte records (16-byte name, 4-byte type, 4-byte value at +20):

| Tunable | Value | Meaning [inferred from names] |
| --- | --- | --- |
| `hwp` | on | XCPM drives HWP |
| `epp` | **0x80** | energy/performance preference, balanced |
| `perf-bias` | 5 | |
| `utility-tlvl` / `non-focal-tlvl` | 0x35 / 0xfa | |
| `ratioratelimit` | 3,000,000 ns | matches `machdep.xcpm.ratio_change_ratelimit_ns` |
| `io_epp_boost` | 0x20 | |
| `lpm_ratio` | 26 | matches `lpm_plimit_max_100mhz_ratio` |

EPP 0x80 on a hybrid Raptor Lake part may be enough to keep all cores near base clock [inferred]. XNU has
`machdep.xcpm.epp_override` (0 here), so **EPP-1** (`tools/cpu/epp.sh`) sweeps it at runtime: 128 (control), 64,
32, 1, one thread and 12 threads per value, package power sampled. No reboot, no EFI change. If a lower EPP lifts
the all-core clock, CPUFriend with an edited vector makes it permanent; if the kernel refuses the write or nothing
moves, EPP is ruled out and the limit is elsewhere (HWP min/max, the EC, or PL1/PL2 as XCPM programs them).

**AGPM-1b** (same boot, `agpm.sh check 2` at 19:45, 13 min uptime, load 1.58) [measured]: RC6 73-90 % per 0.5 s
sample, so it holds well past the 50-80 s where #87 saw it switch off. Idle package 7.3 W; PC2 only ~2 % this time,
so the ~51 % of AGPM-1 is not stable and something else (apps awake, LTR) keeps the package in C0 most of the time
[inferred]. 1 thread 2.82 GHz avg; 12 threads 26.7 GHz-equiv at 18.8 W, still no all-core turbo. This was the
armed one-boot config; `agpm.sh keep` was already written for the next boot.

**EPP-1** (`epp.sh 1`, 19:49, load 4.32) [measured]: `sysctl: oid 'machdep.xcpm.epp_override' is read only`, even as
root, so EPP cannot be changed at runtime. As booted: 1 thread 2.90 GHz, 12 threads 27.3 GHz-equiv at 18.0 W.
EPP is neither confirmed nor ruled out. The only way to change it is to replace the frequency vector at boot:
CPUFriend (Lilu plugin) with a data provider built from this Mac's own board-id plist with `epp` 0x80 → 0x20 and
nothing else changed (CPUFRIEND-1).

**CPUFRIEND-1 built** (`tools/cpu/cpufriend.sh`, 2026-11-22). CPUFriend 1.3.0 RELEASE from acidanthera's GitHub
releases (zip sha256 `37645d96`, unsigned like every Lilu plugin), unpacked in `~/nmx-build/cpufriend/dl/x`. The
data provider is the ResourceConverter.sh personality (AppleACPICPU on `processor`, probe score 1100) whose
`cf-frequency-data` is this Mac's own `Mac-E1008331FDC96864.plist` with the `epp` record set to 0x20 in all three
vectors. Dry run: one byte differs per vector (offset 7220) and everything else is identical [measured]. It loads
after WhateverXe and AGPMNoRC through a new `EXTRA_KEXTS` knob in `efi.sh` / `wex-config.py`.

### CPUFRIEND-1 result (boot 19:56, check 19:59, load 3.12 / 4.43) [measured]

`cpufriend.sh check 1`: `org.acidanthera.driver.CPUFriend (1.3.0)` loaded, `cf-frequency-data` on 12 entries,
`vectors_loaded_count 1`, RC6 77-91 %. Idle 7.2 W; 1 thread 2.36 GHz avg (max 3.47); 12 threads 23.6
GHz-equiv at 17.5 W. With EPP 0x20 nothing improved (this boot was busier than AGPM-1b), so **EPP is not the limit**
[inferred, one run].

**The real ceiling: no CPU ever runs above 3600 MHz.** The highest per-CPU "CPU Average frequency" in each
powermetrics run: base 3597, agpm-1 3599, agpm-2 3600, cpuf-1 3600 MHz [measured]. And under 12 busy threads the
per-CPU clocks split into groups instead of all turboing (average MHz per CPU in the multi phase):

| Run | CPU 0-1 | 2-3 | 4-5 | 6-7 | 8-11 |
| --- | --- | --- | --- | --- | --- |
| base | 1753-1790 | 3513-3589 | 1478-1497 | 999 | 2615-2698 |
| agpm-2 | 3587 | 3540-3591 | 2376-2405 | 1505 | 1987-2000 |
| cpuf-1 | 3579-3594 | 1581-1584 | 1582-1585 | 1578-1581 | 2042-2052 |

**Explanation [inferred, strong]:** on Alder Lake and Raptor Lake, P-core HWP performance levels are not 100 MHz
ratios. One level is 78.741 MHz, the `hybrid_scaling_factor` Linux's intel_pstate uses for these parts (Wysocki,
LKML 2022-10 and 2024-12). XCPM treats this CPU as a Comet Lake part and writes ratio units. Its ceiling,
`hard_plimit_max_100mhz_ratio 46`, lands at 46 × 78.741 = **3622 MHz** on a P-core: the measured cap. Every P-core
request is scaled down the same way (4.6 GHz becomes 3.6, 2.1 becomes 1.65).

Since HWP itself mistranslates the ratios, the next test switches HWP off in the vector (`hwp` on → off,
CPUFRIEND-2). XCPM then drives legacy P-states through `IA32_PERF_CTL`, which uses real 100 MHz ratios on both
core types. Risk: if firmware has already enabled HWP (`IA32_PM_ENABLE` is one-way until reset), PERF_CTL is
ignored and the cores run on HWP's own autonomous choice. Either result is informative.

Sources: [LKML, intel_pstate hybrid P-core scaling factor](https://lkml.iu.edu/hypermail/linux/kernel/2210.3/03224.html),
[LKML, per-model scaling factors](https://lkml.indiana.edu/hypermail/linux/kernel/2412.0/06583.html).

`HWP=off cpufriend.sh arm`: the vectors with `hwp` off, epp untouched; AGPMNoRC as daily. CPUFriend loaded,

| Phase | CPUFRIEND-1 (HWP on) | CPUFRIEND-2 (HWP off) |
| --- | --- | --- |

Windows; idle efficiency (~10 %) and the GPU are what is left. Weighted total ~65-70 %.

### After CPUFRIEND-2: what is left (2026-11-22)

CPU throughput is done: ~95 % single thread, ~90 % all-core [inferred from CPUFRIEND-2]. What is left is idle and
battery efficiency, ranked by expected gain:

1. **RTX never powers off at runtime** (status open problem 1). An awake RTX 3050 Laptop idles at a few watts on

2. **Idle with HWP off** (10.8 W against 7.2 W with HWP). Read `cpufriend.sh check 3` after a quiet uptime first;
   the 10.8 W came from a 3-minute uptime under load 5.5.
3. **Package C-states**: still PC2 at best; Linux reaches PC8. LTR/USB/Bluetooth as in WhateverXe #87.
4. Sleep stays off (untested with WhateverXe): no saving with the lid closed.

The CPU name in About This Mac stays "Unknown": `revpatch=cpuname` (RestrictEvents 1.1.6) crashed System Settings
and `system_profiler` in AppleSystemInfo (XE-12, `KERN_MEMORY_ERROR`), and removing it fixed that (XE-13)

### RTD3-0 built: find the RTX's power resource (2026-11-22)

Goal: the RTX powered off unless an `ondemand.sh` app uses it. nullmoth 3.0 (installed) has an opt-in D3cold
monitor [measured, `strings` of NVRM 3.0 and `kexts/NVRM/nv_rtd3.cpp` at `87e524a`]: with `nvrtd3=1` and
`nvrtd3res=<ACPI path of the power resource>` it suspends the GPU and runs the resource's `_OFF` after 60 s with no
NVIDIA framebuffer and no user client on NVRM or the NV accelerator, and `_ON` when one appears. Upstream: "not
measured on hardware".

On our idle desktop the conditions hold [measured 20:2x]: no `NVRMNVDAFramebuffer` (the IOFramebuffers are the three
`AppleIntelFramebuffer`), NVAccel's 32 children are `IOAccelNVRMCarrier` (IOService, not user clients), NVRM's are
`NVRMDisplay`. The RTX is `\_SB.PC00.PEG0.PEGP` [measured, ioreg `acpi-path`]. The power resource name is not
visible from macOS (no "ACPI Tables" property, power resources are not in the ACPI plane), and guessing (`PXP_`

lists every `PowerResource` and `_PR3` (small AML scan; `iasl` could not be installed, Homebrew needs sudo for
`/usr/local/libexec`). RTD3-1 then sets `nvrtd3=1 nvrtd3res=<path>`.

### RTD3-0 result: the power resource is `\_SB.PC00.PEG0.PXP_` (2026-11-22)

The dump (boot 20:27, `~/rtd3-acpi.txt`, tables in `~/nmx-build/acpi/ACPI`) [measured]:

- SSDT-12 (29405 bytes) holds `PowerResource PXP_` at 0x49f6-0x4dd0 inside `Scope \_SB.PC00.PEG0` (0x2f11-0x51b7).
  It has `_STA` (reads `GPRS`), `_ON_` (`GC6O`, `DGCX`, `TDGC`, `PON_`, `L23D`: leave GC6, retrain the link) and
  `_OFF` (`GC6I`, `DL23`, `POFF`, touches `EC0_`): the usual NVIDIA RTD3/GCOFF sequence. No `_OSI` in the table, so
  nothing gates it on Windows.
- In the same scope, `_PR0` and `_PR3` are Methods (0x518e) returning `PXP_`, not `Name(_PR3, Package)`, which is
  why the RTD3-0 scan listed no `_PR3` for PEG0. The ~40 `NVPR` resources are per-root-port (RP01-RP28, PEG0-3,
  PRT0-7) inside `If (STD3)` blocks of another scope (`VR3D`/`VS3D` methods), not the RTX's.
- SSDT-19's `PCRP` (`_PR3` x3, near `HGOF`) is not under PEG0; left alone.

### RTD3-2 result and the cause: macOS takes 4-character names only (2026-11-22)

RTD3-2 (boot 20:48) [measured]: `RTD3 \134_SB.PC00.PEG0.NXPR._OFF -> 0xe00002c2` at 20:51:09, after an RM standby of
5.3 s, and the same at 20:50 (sleep #1); "power-off failed, GPU resumed and left on" each time. The wrapper's return
value changed nothing, so H1 is ruled out.

Disassembly of `AppleACPIPlatformExpert::evaluateObject(IOACPIPlatformDevice*, const OSSymbol*, ...)` in
`/System/Library/KernelCollections/BootKernelExtensions.kc` (fileset entry `com.apple.driver.AppleACPIPlatform`,
symbol at `0xffffff8001407110`) [measured]:

```
071a4  movl  $0xe00002c2, %r12d     ; kIOReturnBadArgument
071aa  movq  -0x30(%rbp), %rdi      ; the OSSymbol name
071b3  callq *0x130(%rax)           ; getLength()
071bc  cmpl  $0x4, %eax
071bf  ja    -> return %r12d
```

So a name is one NameSeg (at most 4 characters) relative to the device; no absolute path, no dots. nullmoth's
`rtd3Acpi` takes the first `IOACPIPlatformDevice` above NVRM, which is `PC00` (`\_SB.PC00`; ioreg: PC00 →
AppleACPIPCI → PEG0 → IOPP → PEGP → NVRM) [measured], and evaluates `"<nvrtd3res>._OFF"`: no `nvrtd3res` can pass.
This is a nullmoth bug (upstream says RTD3 was "not measured on hardware"); worth reporting to them.

Why `_ON_` fails, from the AML of SSDT-12 (hand-decoded, iasl not installed):
- `_ON_` (0x4a76): `If (VDID == Ones) {} Else { If (GPRS == 0) {} Else { If (CondRefOf (PEGP.NVID)) { If (DGPV ==
  0x10DE) { If (NVGE >= 0x14) { If (PEG0.GSTA != 0) { Return (0) } } If (TDGC == 1) { GC6O path } Else { PON_, L23D,
  CMDR = 7, D0ST = 0, While (PEGP.NVID != 0x10DE) { Sleep (1) }, LREN = PEGP.LTRE, CEDR = 1, PEGP.SSSV = DSSV,
  Sleep (100) } } } Else { PON_, L23D } } } EC0_.VGAF = 1, EC notify`. `VDID` resolves to PEG0's (the root port).
- `GSTA` (SSDT-15) returns `\_SB.GGIV (PEGP.PWGD)`, the power-good GPIO. `_OFF` returns early unless it is 1.
- `POFF` (SSDT-12 0x509b) asserts reset (`PIN_ON (RSTG)`), but it cuts the rail (`PIN_OFF (PWRG)`) only when `GPPR` returns 1.
  `GPPR` returns 0 when `WAKP != 0 && WKEN == 0`, or when `PCPB` or `DVES` say so.
  `PON_` powers the rail, waits for PWOK and releases reset.

The normal `_ON_` branch waits in a loop until `NVID` reads NVIDIA's ID, plus `Sleep (100)`. It cannot return while
the GPU is off the bus. `NXO` came back in the same millisecond as the wake line, and `_OFF` took about 150 ms. So
`_ON_` most likely returned early through the `GSTA != 0` check: power-good stayed high because `POFF` left the rail
on (`GPPR` = 0), and the GPU stayed in reset [inferred]. Which branch it took is [unverified]: NVRM logs only the
evaluate status. If the rail stays on, RTD3 saves less than a full D3cold. The ~26 W reading would fit that, but it is
not evidence for it.

### RTD3-4 built: `NXO_` finishes the power-up when `_ON_` did not (2026-11-22)

One variable: `NXO_` in `SSDT-NXRTD3.aml` (405 bytes, `e31e1f30`, checksum and every PkgLength checked by hand).
After `PXP_._ON_ ()`, `If (PEGP.NVID != 0x10DE)` it runs the rest of `_ON_`'s normal branch itself. The steps are

`CEDR = 1`, `PEGP.SSSV = DSSV`, `Sleep (100)` and `EC0_.VGAF = 1`. Then it returns 2.
The EC notify (`EC6E = 0xD1`, `EDTA = 5` under mutex `NVYY`) is left out.
NVRM (`986b14bc`) and `NXOF` are unchanged. If `_ON_` worked, `NVID` is already NVIDIA's and nothing extra runs.

Risk: same as RTD3-3; a failed power-up leaves the RTX LOST until reboot. The daily config is unaffected.
