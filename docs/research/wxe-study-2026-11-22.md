# How much of the i5-13420H the hackintosh uses, and is a WhateverXe fork worth it (2026-11-22)

> **Summary.** Measured and estimated how much of this laptop's hardware macOS uses today, compared with Windows
> and Linux on the same chip. Overall **~45-60 %** [inferred, wide range]. CPU clocks are the largest gap: single
> thread peaks at 3.55 GHz against a 4.6 GHz spec. Idle efficiency is the worst. Our AGPM profile carries the
> `RCxControl` block that kills GT RC6 (WhateverXe #87) [measured: present]. Most of the gain sits **outside**
> WhateverXe (CPU config, AGPM, power states), so the verdict is: no full fork, keep a thin patch series on upstream.

Related: [xe-latency.md](xe-latency.md), [radar-2026-11-22.md](radar-2026-11-22.md),
[xe-alternatives.md](xe-alternatives.md), [../knowledge/hybrid-route.md](../knowledge/hybrid-route.md),
`tools/cpu/clockprobe.c`, `tools/cpu/cpu-study.sh`.

## 1. The metric

**Extraction % = what macOS gets ÷ what the best of Windows or Linux gets on the same (or same-class) hardware**,
one number per area, then a weighted total. Windows is the 100 % reference because Acer tunes its firmware for it;
Linux is shown where it beats Windows.

## 2. Reference numbers (Windows / Linux)

- **CPU, Windows, this exact model (ANV15-51, i5-13420H):**
  - Cinebench R23: 13,731 MT / 1,860 ST (TechRadar).
  - Package power under load: ~104 W in the first seconds, ~79 W at 15-30 s, ~55 W sustained (LaptopMedia).
  - Geekbench 6 medians across sites: 2,186-2,320 ST and 8,444-9,760 MT (Notebookcheck, cpu-monkey, nanoreview).
- **CPU, Linux vs Windows:** Phoronix measured Linux ~14-15 % faster on CPU geomeans on Meteor Lake and Lunar Lake
  [measured by them, other chips; inferred to hold roughly here].
- **iGPU, Linux vs Windows:** the Intel iGPU is often a little slower on Linux than on Windows. Windows stays the
  iGPU reference.
- **Idle, Linux:** on an RPL-P XPS 13 Plus 9320 (same display IP as ours), Linux idles at **0.88 W package** with
  PC8 at 79 %. macOS with WhateverXe idles at 4.37 W and never goes below PC6 (jkbuha, WhateverXe #87).

## 3. Our machine today [measured 2026-11-22 19:20 unless noted]

- **Setup:** XE-15c (WhateverXe 0.8.3 + our patches), `-wex-objpreempt -wex-noccs -wex-hostrps-max`,
  `-disablegfxfirmware`, SMBIOS MacBookPro16,1, CPUID spoofed to Comet Lake.
- **Topology:** XNU sees 12 identical CPUs.
  - `hw.perflevel0.physicalcpu: 12`, no `perflevel1`.
  - `machdep.cpu.thermal.hardware_feedback: 0`, so no Thread Director/HFI.
  - CpuTopologyRebuild is in the EFI but disabled (`make_config.py` line 36). There is no CPUFriend.
- **CPU clock** (`clockprobe`: a dependent `add reg,reg` chain, one add per cycle, on AC, load average ~2.8):
  - Single thread: peaks at 3.55-3.56 GHz, then falls to 1.84-3.24 GHz. Windows boosts to 4.6.
  - 12 threads: 1.65-1.98 GHz per thread, 21.6 GHz-equivalent in total.
  - `pmset -g therm` shows `CPU_Speed_Limit 100` and no thermal warnings.
  - Caveat: the 2.8 load average from other apps lowers these numbers. `cpu-study.sh` repeats the run with power
    data.
- **iGPU:**
  - The GT is pinned at RP0 (1400 MHz requested, ~1.1 GHz granted). RC6 is never entered (XE-15).
  - FMA throughput is ~711 GFLOPS against a theoretical 1,075 (66 %).
  - GuC/HuC are off, so the CPU submits GPU work. The CCS ring is off (`-wex-noccs`).
- **AGPM:** `ioreg` has **one `RCxControl` entry**: `RC6_Wake_Limit=40, RC6_Threshold=520, RC_Eval_Interval=40000,
  RP_Idle_Hysteresis=25`. It sits next to a `CPGControl` entry.
  - These are the exact values rodgod-rr found killing GT RC6 50-80 s after boot on a MacBookPro16,1 RPL-HX (#87).
  - So our "RC6 never entered" is probably AGPM, not only `-wex-hostrps-max` [inferred, strong].
- **Bluetooth:** state Off (`BCM_4350C2`). The #87 PC2 blocker (Intel CNVi BT) probably does not apply as-is
  [unverified].

## 4. Extraction by area

Estimates; the inputs are listed so each can be replaced by a measurement.

| Area | Weight | macOS today | Reference | Extraction | Basis |
| --- | --- | --- | --- | --- | --- |
| CPU single thread | 20 % | 3.55 GHz peak, ~2.5 sustained; thread may land on an E-core | 4.6 GHz P-core (Windows); Linux +~10 % | **~55-75 %** | clock ratio [measured clock, inferred score] |
| CPU multi thread | 20 % | 21.6 GHz-equiv (12 threads) | ~35-40 GHz-equiv at 55-79 W [inferred from Windows power data] | **~55-65 %** | [inferred] |
| Idle / battery efficiency | 15 % | GT in C0 100 %, no RC6, package ≥ PC6 or worse | Linux 0.88 W package, PC8 | **~20-30 %** | #87 numbers, our RC6 state [inferred] |
| iGPU throughput | 15 % | 66 % of FMA peak, ~1.1 GHz | Windows ~85-90 % of peak [unverified] | **~75 %** | [measured ours, unverified reference] |
| iGPU latency / smoothness | 15 % | max submit wait 0.2-2 ms (XE-15); 100 ms fence-timer stalls possible (#130) | GuC + i915/Windows scheduling | **~70 %** | [inferred] |
| Media engines | 10 % | no HuC; VP9/AV1 gaps on ADL-class (#133); HEVC/H.264 state unchecked | full decode/encode | **~50 %** | [unverified for us] |
| Display | 5 % | 144 Hz with `refresh.sh`; no PSR, FBC, DC states | full | **~85 %** | [measured Hz, inferred power] |

**Weighted total: ~55 % (range 45-65 %)** of what Windows gets out of the same machine.

- CPU and idle efficiency pull it down most. The iGPU itself is closer than it feels day to day.
- With Linux as the CPU reference, the CPU rows drop another ~10 %.

## 5. What is left, ranked by gain ÷ effort

1. **CPU clocks and power (config only, no kext code):**
   - First find why a single thread stops at 3.55 GHz. Suspects [unverified]:
     - the Acer EC performance mode carried over from Windows (Quiet/Balanced caps PL1/PL2);
     - EPP/HWP hints from the MacBookPro16,1 frequency vectors with no CPUFriend;
     - the iGPU pinned at RP0 with no RC6, using up the shared package budget;
     - E-core placement.
   - Then, one variable each: CPUFriend with a vector built for this chip, then CpuTopologyRebuild (#5 on the
     Dortania/b00t0x list; mixed anecdotes, one ~1535→1863 Geekbench ST report).
   - Gain: CPU rows from ~60 % toward ~90 %. Biggest single item.
2. **AGPM injector without `RCxControl`/`CPGControl` (codeless kext, ~30 lines of plist):**
   - rodgod-rr went from GT RC6 0 → 96 % and package PC2 0 → 89 % with it.
   - For us: lower idle power, cooler package, and more turbo budget left for the CPU (feeds item 1).
   - Test it alone, with `-wex-hostrps-max` unchanged.
3. **#130 fence timer (`IOAccelFenceMachine` quantum 100 ms):**
   - Not in 0.8.3 (no match in `src-083`).
   - gianguyen14 confirmed the binary site on **Sequoia 15.8.1**. With `-wexfencepoll` (2 ms quantum): 0 completions
     over 50 ms vs 90-150 ms stalls without it.
   - Small patch on our series; fits the lag work directly.
4. **Package C-states below PC6 at idle:**
   - Check `PKGC_BREAK_CAUSE_*` through IOReport `pmtelemetry_cpu` (no sudo needed).
   - Then look at PCH xHCI LTR and Bluetooth, as in #87.
5. **#176 governor:** already built (XE-15g). Only useful once RC6 works (item 2).
6. **Display DC states / PSR / DMC on display13:** large work. Upstream contributors with the same display IP are on
   it: jkbuha (RPL-P) on the ADL-P DMC loader, brandonedley on DC9 teardown for sleep (PC10 99 %). Follow, don't
   lead.
7. **GuC/HuC submission:** the root of CPU-dependent GPU latency and of missing HuC media/FairPlay (#48). The
   hardest item, and nobody has a working path. Not a goal.

## 6. Fork verdict

**No separate WhateverXe project.** Keep what we have: a short patch series (`0001..0004`) rebased on each upstream
release, plus one small kext or config change per item above.

- Items 1, 2 and 4 are not WhateverXe code. A fork would not get them faster.
- Upstream moves weekly (0.8.0 → 0.8.3 in two weeks). It has active contributors on our exact display IP and
  SMBIOS: jkbuha (RPL-P display13), rodgod-rr (RPL-HX, MacBookPro16,1).
- A hard fork would pay the rebase cost alone and lose their fixes.
- Where a patch is ours (objpreempt, noccs, fence poll), post it upstream as a PR or an issue comment with numbers.
- Revisit if upstream stalls for a month or rejects a change we depend on.

## 8. CPU-1 baseline run, `cpu-study.sh base` (2026-11-22 19:27, on AC, XE-15 daily boot) [measured]

`~/cpu-study-base.txt` (7,600 lines; powermetrics `cpu_power,gpu_power`, 1 s samples). Load average at start was
1.40 / 1.94 / 2.01, so Claude, Discord and others were running.

| Phase | Package (energy model) | Package C-states | CPU clock |
| --- | --- | --- | --- |
| idle, 20 s | **11.7 W** avg, 15.4 max | **0 % in every PC state** (C2-C10) | 1.34 GHz system avg; P-cores ~0 % C6 |
| 1 thread, 22 s | 12.2 W avg | 0 % | `clockprobe` 1.24-3.57 GHz, mostly 1.5-2.5; peak 3.60 GHz (powermetrics) |
| 12 threads, 30 s | **19.2 W** avg, 20.9 max | 0 % | **2.18 GHz** avg per CPU; `clockprobe` 24.0-25.6 GHz-equiv |

- **The package never leaves C0, even at idle.** P-cores almost never reach C6. They see thousands of very short
  wakes per second (CPU 0: ~5,000/s active periods under 16 µs).
- **All-core load stays at ~2.2 GHz and 19 W.** That is about the i5-13420H base clock (P 2.1 GHz). Windows holds
  ~55 W sustained, so the CPU is not power- or heat-limited here: it just isn't asking for turbo. Single-thread turbo
  shows up only in short bursts.
  - Suspect: XCPM / HWP requests from the spoofed Comet Lake identity and the MacBookPro16,1 frequency vectors
    (CPUFriend item) [inferred].
  - The EC mode is less likely, since power stays far below any PL1 [inferred].
- **powermetrics reports `Performance Limited Due to: GPU LIMIT ICCMAX/PL4/OTHER` in every sample**, idle included.
  What sets it is not known [unverified].
- **powermetrics' GPU section does not read the Xe GT:** 0 MHz, 0 % busy, 100 % "C-state". Use `N97GTPowerSample`
  (`xe15.sh check`) for the GT instead.

**Revised extraction:**
- CPU multi thread ~60-65 %: 25.5 against ~38-40 GHz-equiv at Windows' 55 W [inferred].
- CPU single thread ~45-55 %: ~2.2 GHz sustained against 4.6 GHz.
- Idle efficiency **~10 %**: 11.7 W against Linux's ~1 W on the same class of chip.
- Weighted total stays ~50-55 %.

**Next test, AGPM-1** (`tools/cpu/agpm.sh`): one boot of the daily XE-15 config plus `AGPMNoRC.kext`. That is a
codeless re-injection of this board-id's AGPM profile without `RCxControl` and `CPGControl`, generated from the
system's own AGPM Info.plist. One variable.
- Want: GT RC6 > 0 % in `xe15.sh check`, lower idle package power, any PC state above 0 %.
- If the CPU clock also rises, the GT was eating the budget; if not, CPUFriend is next.

## 9. AGPM-1, AGPM IGPU profile without RCxControl and CPGControl (2026-11-22 19:32 boot) [measured]

One boot of the XE-15 daily config plus `AGPMNoRC.kext` (`agpm.sh arm`). `agpm.sh check 1` at 19:34: `RCxControl`
0 and `CPGControl` 0 in `ioreg`, the AGPMController personality has `IOProbeScore 5000`. `kextstat` lists nothing
because the kext is codeless. Files: `~/agpm-1.txt`, `~/xe15-agpm-1.txt`, `~/cpu-study-agpm-1.txt`.

- **GT RC6 98.9-99.3 %** in `xe15.sh check` (XE-15c: 0 %, counter frozen). Still **91.1 %** at 5 min uptime, so it
  does not switch off after 50-80 s as on #87. GT answer still 1400 MHz (RP0, `-wex-hostrps-max`).
- kernel->gpu p50 0.07 ms, p99 0.25 ms, max 0.98 ms: no worse than XE-15.
- Load average was 15.2 / 8.25 at the start (boot still settling), so the CPU numbers below are noisy and favour the
  baseline, not this run.

| Phase | Package, CPU-1 → AGPM-1 | Package C-states | CPU clock, CPU-1 → AGPM-1 |
| --- | --- | --- | --- |
| idle | **11.7 → 6.6 W** (min 6.2) | 0 % → **~51 % PC2**, C3-C10 still 0 % | system 1.34 → 1.51 GHz |
| 1 thread | 12.2 → 8.5 W | 0 % | avg 2.25 → 2.48 GHz, max 3.51 |
| 12 threads | **19.2 → 15.9 W** | 0 % | 25.5 → **27.8 GHz-equiv** (+9 %), system 2.42 GHz |

- The AGPM `RCxControl`/`CPGControl` blocks were the cause of RC6 0 % (pitfall confirmed). With the GT able to
  sleep, the package reaches PC2 and idle power drops by 5 W.
- All-core turbo is still missing: 12 threads at ~2.4 GHz and 16 W, far below PL1. The GT was not eating the budget.
- XNU's limits allow turbo: `machdep.xcpm.hard_plimit_max_100mhz_ratio 46`, `soft_plimit_max 46`. The board-id
  plist (`X86PlatformPlugin/Mac-E1008331FDC96864.plist`) carries `CPUFloor 1000`, `BoostLimit 0` and three
  frequency vectors keyed for 4500/4800/5000 MHz (Comet Lake parts). `lpm_plimit_max_100mhz_ratio 26`, low power
  mode off [measured]. Whether the vectors' EPP/HWP request holds the all-core clock down is the next test [inferred].

**Revised extraction:** idle efficiency ~10 % → ~15-20 % (6.6 W against ~1 W) [inferred]; CPU multi ~65-70 %.
Weighted total ~55-60 %.

**Next:** make AGPM daily (`agpm.sh keep`), confirm RC6 holds over a long uptime (`agpm.sh check 2`), then CPUFriend
with a frequency vector built for this CPU (one variable: the vector).

## 10. The board-id frequency vector, decoded (2026-11-22) [measured]

`X86PlatformPlugin.kext/Contents/Resources/Mac-E1008331FDC96864.plist` holds three 7,668-byte `FrequencyVectors`;
vectors 0 and 1 are identical and 2 differs only in four ratio thresholds. `machdep.xcpm.vectors_loaded_count 1`,
X86PlatformPlugin and X86PlatformShim are active, `plugin-type 1`. The tunables block at the end of each vector is a
list of 36-byte records (16-byte name, 4-byte type, 4-byte value at +20):

| Tunable | Value | Meaning [inferred from names] |
| --- | --- | --- |
| `hwp` | on | XCPM drives HWP |
| `epp` | **0x80** | energy/performance preference, balanced |
| `perf-bias` | 5 | |
| `utility-tlvl` / `non-focal-tlvl` | 0x35 / 0xfa | |
| `ratioratelimit` | 3,000,000 ns | matches `machdep.xcpm.ratio_change_ratelimit_ns` |
| `io_epp_boost` | 0x20 | |
| `lpm_ratio` | 26 | matches `lpm_plimit_max_100mhz_ratio` |

EPP 0x80 on a hybrid Raptor Lake part may be enough to keep all cores near base clock [inferred]. XNU has
`machdep.xcpm.epp_override` (0 here), so **EPP-1** (`tools/cpu/epp.sh`) sweeps it at runtime: 128 (control), 64,
32, 1, one thread and 12 threads per value, package power sampled. No reboot, no EFI change. If a lower EPP lifts
the all-core clock, CPUFriend with an edited vector makes it permanent; if the kernel refuses the write or nothing
moves, EPP is ruled out and the limit is elsewhere (HWP min/max, the EC, or PL1/PL2 as XCPM programs them).

**AGPM-1b** (same boot, `agpm.sh check 2` at 19:45, 13 min uptime, load 1.58) [measured]: RC6 73-90 % per 0.5 s
sample, so it holds well past the 50-80 s where #87 saw it switch off. Idle package 7.3 W; PC2 only ~2 % this time,
so the ~51 % of AGPM-1 is not stable and something else (apps awake, LTR) keeps the package in C0 most of the time
[inferred]. 1 thread 2.82 GHz avg; 12 threads 26.7 GHz-equiv at 18.8 W, still no all-core turbo. This was the
armed one-boot config; `agpm.sh keep` was already written for the next boot.

**EPP-1** (`epp.sh 1`, 19:49, load 4.32) [measured]: `sysctl: oid 'machdep.xcpm.epp_override' is read only`, even as
root, so EPP cannot be changed at runtime. As booted: 1 thread 2.90 GHz, 12 threads 27.3 GHz-equiv at 18.0 W.
EPP is neither confirmed nor ruled out. The only way to change it is to replace the frequency vector at boot:
CPUFriend (Lilu plugin) with a data provider built from this Mac's own board-id plist with `epp` 0x80 → 0x20 and
nothing else changed (CPUFRIEND-1).
